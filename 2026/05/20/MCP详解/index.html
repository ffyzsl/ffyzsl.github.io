MCP详解

发表于 2026-05-20 更新于 2026-06-01

1. 什么是 MCP？

想象一下你买了一台新手机，发现它只有一个 USB-C 口。不管是充电、传文件、接显示器还是插耳机，全走这一个口。你不需要为每种外设买不同的线，因为大家都遵循同一种标准。

MCP（Model Context Protocol，模型上下文协议） 就是 AI 世界里的 USB-C。

在没有 MCP 之前，想让 AI 助手连接外部数据源（比如你的数据库、文件系统、GitHub），你需要给每个数据源写一套独立的对接代码。连接 GitHub 时你写一套，连接 PostgreSQL 时你写另一套，连接 Slack 时再来一套。每个数据源的 API 习惯都不一样，维护起来像个噩梦。

MCP 由 Anthropic 提出并开源，它定义了一套统一的标准，让 AI 模型通过同一种方式和任何外部工具、数据源交互。你只需要学会 MCP 这一种协议，就能对接全世界。

一个具体的场景帮你理解

MCP 解决了什么问题？

没有 MCP 有了 MCP
每个数据源写一套对接代码（M × N 问题） 统一协议，对接一次（M + N 问题）
AI 只能利用训练数据回答问题 AI 能实时访问外部数据
工具调用碎片化，每个 AI 框架都有自己的一套 统一标准，一次编写到处运行
上下文信息靠你手动复制粘贴 AI 自动按需获取上下文

2. 核心架构：Host、Client、Server

MCP 采用了经典的 客户端-服务器（Client-Server）架构，其中包含三个角色。用餐厅来类比：

三个角色的正式定义

角色 类比 职责
MCP Host AI 应用本身 管理用户交互、运行 LLM、创建并管理 MCP Client
MCP Client Host 和 Server 之间的”接线员” 每个 Client 维护一条到 Server 的连接，负责收发 JSON-RPC 消息
MCP Server 提供能力的外部服务 暴露 Tools、Resources、Prompts 供 AI 发现和调用

关键理解：一对多

3. MCP 的三大核心原语

MCP Server 能暴露三种能力，这是 MCP 最核心的概念：

原语 谁控制 类比 REST 用途
Tools（工具） 模型控制 POST / PUT 执行操作、写数据、调用 API
Resources（资源） 应用控制 GET 暴露只读数据给模型
Prompts（提示模板） 用户控制 预设模板 可复用的交互模式

3.1 Tools（工具）— 让 AI 动手做事情

Tool 是模型可以调用的可执行函数。模型根据对话上下文，自主决定调用哪个 Tool、传什么参数。

当你对 AI 说 “帮我算一下 123 + 456”，AI 会自动调用 add(123, 456)，拿到 579，然后回答你。

Tool 的关键属性：

属性 说明
name 唯一名称，AI 通过名称来选择和调用
description 告诉 AI 这个 Tool 是干什么的（写得越好，AI 用得越准）
inputSchema JSON Schema，定义 Tool 接受什么参数、每个参数什么类型
annotations 安全标注（是否只读、是否可破坏数据等）

注意 description 里写清楚了参数怎么填——这个细节直接决定了 AI 能否正确调用你的 Tool。

3.2 Resources（资源）— 让 AI 能看到数据

Resource 是只读的数据端点。和 Tool 不同，Resource 不执行任何操作，只是暴露数据。它由应用（Host）决定何时读取。

Resource vs Tool 怎么区分？

Resource Tool
操作类型 只读（不改变数据） 可读可写（可能产生副作用）
谁决定调用 应用（Host） 模型（LLM）
类比 GET /api/users POST /api/users

3.3 Prompts（提示模板）— 让交互更高效

Prompt 是可复用的对话模板。它通常以斜杠命令的形式出现，用户手动触发。

当用户输入 /code_review 并粘贴代码时，这个精心设计的模板会被注入到 LLM 的上下文中，比用户每次手动敲一遍”请审查以下代码…”要高效和一致得多。

5. 传输方式：stdio vs HTTP

MCP 支持两种传输方式，选择哪一档取决于你的部署场景：

传输方式 适用场景 优点 缺点
stdio 本地 Server（和 AI 同机器） 零网络配置、天然安全、延迟极低 只能在本地跑
Streamable HTTP 远程 Server（服务器端部署） 可远程访问、支持多客户端、可负载均衡 需要认证、有网络延迟

stdio 模式（本地）

Host（比如 Claude Desktop）会启动这个 Server 作为子进程，通过管道向它的 stdin 发 JSON-RPC 请求，从 stdout 读 JSON-RPC 响应。因为不走网络，天然安全、延迟接近零。

HTTP 模式（远程）

远程模式支持 OAuth 2.1 认证，适合团队共享 Server 或多客户端同时连接。

7. 进阶：Tool 中使用 Context

Context 是一个强大的参数，当你把它加在 Tool 函数的参数中，MCP 会自动注入，让你在 Tool 内部做些高级操作：

Context 能做什么

方法 用途
ctx.info(msg) / ctx.error(msg) 记录日志
ctx.report_progress(current, total) 报告长任务进度
ctx.read_resource(uri) 在 Tool 内部读取 Resource
ctx.sample(prompt) 让 LLM 生成文本（反向调用）

其中 ctx.sample() 是最特别的能力——它让 MCP Server 反过来请求 LLM 做推理。这意味着你可以写一个 Server，让它在干活的过程中随时调用 AI。

11. 常见问题与坑

坑 1：Tool 描述写得太模糊

Tool 的描述直接决定了 AI 能否正确地选择和正确地调用它。花时间把描述写清楚，比优化代码更重要。

坑 2：stdio 模式下 stdout 被污染

stdio 模式下，Server 通过 stdout 返回 JSON-RPC 消息。如果你的代码里有 print()（输出到 stdout），会破坏 JSON 格式，导致通信失败。日志应该输出到 stderr。

坑 3：Tool 返回的数据太大

如果 Tool 返回了几 MB 的数据，它会作为 JSON 正文传输，拖慢整个对话。对于大数据量，考虑返回摘要或分页结果，或者把数据写入文件，把文件路径作为 Resource 暴露。

坑 4：忘记处理异常

Tool 函数中如果抛出未捕获的异常，MCP 会把它包装成 JSON-RPC 错误返回给 Host。用户看到的可能是”内部错误”这样模糊的提示，而不是有用的信息。

总结

MCP 的核心可以浓缩成三句话：

  1. Tools 让 AI 动手——执行操作、调用 API
  2. Resources 让 AI 看见——暴露数据、提供上下文
  3. Prompts 让用户高效率——复用精心设计的对话模板

三者通过统一的 JSON-RPC 协议，在 Client 和 Server 之间交互。学会 MCP，你就掌握了让 AI 从”只会聊天”进化到”能干活”的关键能力。

概念 一句话
MCP 是什么 AI 的 USB-C 接口 —— 统一的连接标准
Tools 模型控制的函数，让 AI 做事情
Resources 应用控制的只读数据 URI
Prompts 用户控制的对话模板
Host AI 应用本体
Client Host 和 Server 之间的连接器
Server 提供 Tools / Resources / Prompts 的服务
stdio 本地传输（通过管道）
HTTP 远程传输（通过网络）
Context Tool 内部的瑞士军刀（日志、采样、进度）
