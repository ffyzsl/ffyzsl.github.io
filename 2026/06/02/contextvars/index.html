1. 一个问题

两个请求打印出来的都是 Bob。Alice 丢了，因为两个协程共享了同一个 user_name 全局变量，后面的覆盖了前面的。

你可能想：那就别用全局变量，用函数参数传呗？但如果调用链很深——A 调 B、B 调 C、C 调 D，只有 D 需要用到 user_name——你要从 A 一路传到 D：

这种**”漏斗传参”让人崩溃。Python 3.7 引入的 contextvars 就是为了解决这个问题——不用显式传参，每个协程自动拿到自己那份值**。

2. 核心概念：三个角色一台戏

contextvars 模块只有三个核心组件：

组件 一句话解释
ContextVar 变量声明——定义一个上下文变量的”槽位”
Context 值的快照——某个时刻所有 ContextVar 及其值的集合
Token 撤销凭证——set() 返回的令牌，用于恢复旧值

7. 常见坑

❌ 坑 1：忘记 reset(token) —— 上下文泄露

不 reset 的后果：当前协程结束后，如果事件循环重用了同一个协程上下文，下一个请求会拿到上一个请求的脏数据。这种 bug 极其难排查，因为它不是每次都出现。

❌ 坑 2：在函数内部定义 ContextVar

ContextVar 依赖变量名和实例标识来匹配值。同一个模块顶层变量，在解释器生命周期中只存在一个实例，所有代码使用的是同一个”槽位”。

❌ 坑 3：跨线程不自动传播

ContextVar 的上下文是绑定在异步 Task 上的。如果你用 run_in_executor 把代码放到线程池执行，默认情况下线程里拿不到 contextvars：

如何解决？

好在 FastAPI/Starlette 的 run_in_threadpool 已经自动帮你做了这一步，所以大部分情况下你不需要手动处理。

❌ 坑 4：同步依赖中修改变量的值

在 FastAPI 中，同步依赖在 run_in_threadpool 里执行时，ContextVar 的 值拷贝会被注入线程。但你在线程里对 ContextVar 做的修改不会回传到异步层：

解决方案： 使用可变容器（dict、list），通过 .get() 拿到引用，直接修改引用内的内容，而不是调用 .set()：

因为异步层和线程层引用的是同一个 dict 对象（即使 context 被拷贝了，dict 本身的引用没变），修改直接生效。

8. 总结

contextvars 解决的核心问题就一句话：

在异步环境中，让每个协程拥有独立的”全局变量”，无需手动传参。

操作 代码 说明
声明 var = ContextVar('name', default='') 必须在模块顶层
读取 var.get() 取当前协程的值
写入 token = var.set(value) 返回 Token 供恢复
恢复 var.reset(token) 必须用 try/finally
快照 ctx = copy_context() 保存所有变量的当前值
隔离运行 ctx.run(func) 在指定上下文中执行

使用清单：

  • ✅ 在模块顶层定义 ContextVar
  • ✅ 始终提供 default 参数
  • ✅ 用 try/finally 确保 reset(token)
  • ✅ 跨线程时用 copy_context().run()
  • ✅ 同步依赖中用可变容器避开回传问题
  • ❌ 别在函数内部定义 ContextVar
  • ❌ 别在 asyncio 中用 threading.local
