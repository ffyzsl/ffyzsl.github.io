OpenAI和Anthropic对比

发表于 2026-06-02

1. 对比？

当前使用 LLM API 开发应用，主要面对两套接口：OpenAI（Chat Completions / Responses）和 Anthropic（Messages）。OpenAI 已经成为事实上的行业标准，很多第三方模型（DeepSeek、Qwen、GLM 等）都兼容它的接口格式。Anthropic 则走了另一条路，设计上有些关键差异。

2. 基础架构速览

维度 OpenAI Anthropic
核心端点 POST /v1/chat/completions POST /v1/messages
新端点（推荐） /v1/responses（统一 Agent 端点） —
鉴权方式 Authorization: Bearer <key> x-api-key: <key>
版本控制 无（跟随模型） anthropic-version: 2023-06-01 头
System 提示 messages 数组中的 role: "system" 顶层 system 参数（字符串或数组）
max_tokens 可选（不传会有一个默认值） 必填（不传直接报错）
消息角色 system / user / assistant / tool user / assistant（无 system、无 tool 角色）
组织/团队 Organization 头或 project key anthropic-beta 头（开启 beta 功能）

3. 请求体（Request Body）

3.1 OpenAI 请求体

字段说明：

字段 必填 说明
model ✅ 模型 ID，如 gpt-4o、gpt-4o-mini
messages ✅ 消息数组，content 为纯字符串（多模态时可用数组）
max_tokens ❌ 不传有默认值，约 4096
temperature ❌ 0~2，控制随机性
top_p ❌ 核采样
frequency_penalty ❌ -2.0~2.0，抑制重复 token
presence_penalty ❌ -2.0~2.0，鼓励新话题
stop ❌ 停止序列
stream ❌ 是否流式
tools ❌ 工具定义数组
tool_choice ❌ "auto" / "required" / "none" / 指定工具
response_format ❌ 强制输出格式（JSON 模式、JSON Schema）

3.2 Anthropic 请求体

字段说明：

字段 必填 说明
model ✅ 模型 ID，如 claude-sonnet-4-5-20250929
max_tokens ✅ 必须显式指定，上限取决于模型
system ❌ 独立于 messages 之外！（字符串或 content block 数组）
messages ✅ 消息数组，content 可以是字符串或 content block 数组
temperature ❌ 0~1，对推理模型无效
top_p ❌ 核采样
top_k ❌ Top-K 采样（OpenAI 没有此参数）
stop_sequences ❌ 停止序列（最多 10000 个）
stream ❌ 是否流式
tools ❌ 工具定义数组
tool_choice ❌ {type:"auto"} / {type:"any"} / {type:"tool",name:"xxx"}
thinking ❌ 开启扩展思考（仅 Opus 4.5+）
metadata ❌ 自定义元数据，最多 128 个 key

关键差异 1：system 的位置

这样设计的好处：system 和对话历史被物理隔开，更清晰地表达了”系统指令 vs 对话内容”的语义。

关键差异 2：max_tokens 是否必填

Anthropic 必须传入 max_tokens，不传就报错。这是 Claude 的一个保护机制——强制你思考每次请求最多消耗多少 token，防止意外的高额费用。

OpenAI 不传也会工作，但建议显式指定。

4. 响应体（Response Body）

4.1 OpenAI 响应（非流式）

结构特点：

  • 返回一个 choices 数组（默认 1 个，n 参数可请求多个）
  • AI 回复在 choices[0].message.content —— 始终是纯字符串
  • 如果有工具调用，在 choices[0].message.tool_calls —— 和 content 是互斥的（纯工具调用时不返回文本）
  • finish_reason 表示结束原因："stop" / "length" / "tool_calls" / "content_filter"

4.2 Anthropic 响应（非流式）

结构特点：

  • 响应顶层直接就是 message，没有 choices 数组
  • AI 回复在 content 数组里 —— 始终是数组，每个元素是一个 content block
  • 同一个响应里可以同时包含 文本 (text) + 工具调用 (tool_use) + 思考过程 (thinking)
  • stop_reason 表示结束原因："end_turn" / "max_tokens" / "tool_use" / "stop_sequence"

关键差异 4：content 是字符串还是数组

这意味着处理 Anthropic 响应时，你必须遍历 content 数组，不能直接 resp.content[0].text。这也是初用者最容易踩的坑。

关键差异 5：工具调用与文本是否可以同时出现

OpenAI Anthropic
同时返回文本 + 工具调用 ❌ 否（纯 tool_calls 模式不返回文本） ✅ 是（同一个 content 数组中混合 text + tool_use）

Anthropic 的设计更自然——Claude 可以先说一句”让我帮你查一下”，然后调用工具。OpenAI 需要在 tool_calls 之前单独一轮对话来实现这个效果。

关键差异 6：工具结果的角色不同

这是两套 API 最大的”哲学差异”之一：

Anthropic 的设计逻辑是：工具结果是你（开发者）注入到对话中的，本质上属于 user 侧的输入。

6. 工具调用（Tool Calling / Function Calling）

6.1 工具定义格式

OpenAI 工具定义

OpenAI 的工具用 "type": "function" 包裹一层，schema 字段名是 parameters。

Anthropic 工具定义

Anthropic 的工具没有 "type": "function" 包裹，schema 字段名是 input_schema，而不是 parameters。

6.2 tool_choice 控制方式

意图 OpenAI Anthropic
自动决定 "auto" {"type": "auto"}
强制调用 "required" {"type": "any"}
禁止调用 "none" 不传 tools
指定工具 {"type": "function", "function": {"name": "get_weather"}} {"type": "tool", "name": "get_weather"}

6.3 并行工具调用

两者都支持在一次响应中调用多个工具，但细节不同：

OpenAI： finish_reason: "tool_calls"，tool_calls 是一个数组，可以包含多个调用。

Anthropic： stop_reason: "tool_use"，content 数组中包含多个 tool_use 块，还可以同时包含文本。

总结

两套 API 的核心差异可以浓缩成一句话：

OpenAI 把 AI 回复看作”一条消息”（字符串 + 附加的工具调用）；Anthropic 把 AI 回复看作”多个内容块的组合”（文本、工具调用、思考过程共存）。

理解了这一点，其他差异都是由此衍生出来的：

  • 响应格式不同 → 因为一个是单消息，一个是多块数组
  • 工具调用嵌入方式不同 → 因为 Anthropic 的 content 数组天然支持混合
  • 流式事件不同 → 因为 Anthropic 需追踪每个块的 start/delta/stop
  • 工具结果角色不同 → 因为 Anthropic 不希望引入 tool 这个第三种角色

如果你习惯了一套 API，切换时最容易出错的地方是：

  1. 忘记 Anthropic 的 max_tokens 是必填的
  2. 用 resp.content[0].text 直接取 Anthropic 的回复（应该遍历 content）
  3. **把 Anthropic 的工具结果写成 role: "tool"**（应该写 role: "user"）
  4. **在 Anthropic 的 messages 里加了 role: "system"**（应该用顶层的 system 参数）
